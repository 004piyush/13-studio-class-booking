# Schema

## Table-by-Table Column Specifications & Types

### 1. `users`
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `name`: `VARCHAR(255) NOT NULL`
- `email`: `VARCHAR(255) NOT NULL UNIQUE` (indexed: `idx_users_email`)
- `password_hash`: `VARCHAR(255) NOT NULL`
- `role`: `VARCHAR(32) NOT NULL` (`STAFF` or `INSTRUCTOR`)
- `created_at`: `TIMESTAMP NOT NULL`
- `updated_at`: `TIMESTAMP NOT NULL`

### 2. `studio_classes`
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `title`: `VARCHAR(255) NOT NULL UNIQUE` (indexed: `idx_classes_title`)
- `description`: `TEXT`
- `discipline`: `VARCHAR(100) NOT NULL` (e.g. Yoga, Pilates, HIIT, Cycling)
- `default_duration_minutes`: `INTEGER NOT NULL CHECK (default_duration_minutes > 0)`
- `default_capacity`: `INTEGER NOT NULL CHECK (default_capacity > 0)`
- `archived`: `BOOLEAN NOT NULL DEFAULT FALSE` (indexed: `idx_classes_archived`)
- `created_at`: `TIMESTAMP NOT NULL`
- `updated_at`: `TIMESTAMP NOT NULL`

### 3. `class_sessions`
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `studio_class_id`: `BIGINT NOT NULL REFERENCES studio_classes(id)` (indexed: `idx_sessions_studio_class`)
- `session_date`: `DATE NOT NULL`
- `start_time`: `TIME NOT NULL` (composite indexed: `idx_sessions_date_time` on `session_date, start_time`)
- `duration_minutes`: `INTEGER NOT NULL CHECK (duration_minutes > 0)`
- `capacity`: `INTEGER NOT NULL CHECK (capacity > 0)`
- `room`: `VARCHAR(100) NOT NULL`
- `primary_instructor_id`: `BIGINT NOT NULL REFERENCES users(id)` (indexed: `idx_sessions_primary_instructor`)
- `version`: `BIGINT NOT NULL DEFAULT 0` (JPA `@Version` optimistic locking counter)
- `created_at`: `TIMESTAMP NOT NULL`
- `updated_at`: `TIMESTAMP NOT NULL`

### 4. `session_co_instructors` (Join Table)
- `session_id`: `BIGINT NOT NULL REFERENCES class_sessions(id) ON DELETE CASCADE`
- `instructor_id`: `BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE`
- `PRIMARY KEY (session_id, instructor_id)`

### 5. `members`
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `name`: `VARCHAR(255) NOT NULL`
- `email`: `VARCHAR(255) NOT NULL UNIQUE` (indexed: `idx_members_email`)
- `membership_expiry_date`: `DATE NOT NULL` (indexed: `idx_members_expiry`)
- `dismissed_for_expiry_date`: `DATE NULL`
- `created_at`: `TIMESTAMP NOT NULL`
- `updated_at`: `TIMESTAMP NOT NULL`

### 6. `bookings`
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `member_id`: `BIGINT NOT NULL REFERENCES members(id)` (indexed: `idx_bookings_member`)
- `class_session_id`: `BIGINT NOT NULL REFERENCES class_sessions(id)`
- `status`: `VARCHAR(32) NOT NULL` (`BOOKED`, `WAITLISTED`, `CANCELLED`, `ATTENDED`, `NO_SHOW`)
- `created_at`: `TIMESTAMP NOT NULL`
- `updated_at`: `TIMESTAMP NOT NULL`
- Indexed: `idx_bookings_session_status` on `(class_session_id, status)`

### 7. `booking_histories` (Append-Only Audit Trail)
- `id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `booking_id`: `BIGINT NOT NULL REFERENCES bookings(id)` (indexed: `idx_history_booking_id`)
- `old_status`: `VARCHAR(32) NULL`
- `new_status`: `VARCHAR(32) NOT NULL`
- `changed_by_user_id`: `BIGINT NULL REFERENCES users(id)`
- `note`: `TEXT NULL`
- `created_at`: `TIMESTAMP NOT NULL` (indexed: `idx_history_created_at`)

## Relationship Cardinality

- **One-to-Many:**
  - `StudioClass` (1) ➔ `ClassSession` (N): A class template defines defaults for multiple scheduled sessions.
  - `User` (1 primary instructor) ➔ `ClassSession` (N): An instructor is assigned as primary instructor to multiple sessions.
  - `Member` (1) ➔ `Booking` (N): A member books multiple sessions over time.
  - `ClassSession` (1) ➔ `Booking` (N): A session holds multiple participant bookings.
  - `Booking` (1) ➔ `BookingHistory` (N): A single booking lifecycle transitions through multiple immutable audit entries (`BOOKED`, `CANCELLED`, `ATTENDED`, etc.).
  - `User` (1) ➔ `BookingHistory` (N): A staff member or instructor triggers audit history entries.

- **Many-to-Many:**
  - `ClassSession` (M) ➔ `User` (N) via `session_co_instructors`: Multiple co-instructors can assist on a single session, and an instructor can co-instruct across multiple sessions.

## Database vs. Application Constraints

| Constraint / Rule | Enforced By | Why Enforced Here |
| :--- | :--- | :--- |
| Primary keys, unique emails, unique class titles | **PostgreSQL (DB)** | Hard database uniqueness guarantees zero duplicate accounts or class titles regardless of concurrency. |
| Foreign keys & referential integrity | **PostgreSQL (DB)** | Enforces that bookings, sessions, and histories cannot point to orphaned entities. |
| Immutability of `booking_histories` | **JPA (`updatable=false`) + DB + No Update APIs** | Hibernate omits update statements on columns configured with `updatable = false`; the service layer exposes only append methods. |
| Concurrency-safe capacity & waitlist ordering | **Java Service + Pessimistic Row Lock (`PESSIMISTIC_WRITE`)** | PostgreSQL foreign keys and check constraints cannot evaluate dynamic row counts under high concurrency without row-level serialisation on the parent `ClassSession`. |
| Prevent duplicate active booking | **Java Service (+ DB Partial Index)** | A member cannot double-book a session while active, but may legitimately re-book if they previously cancelled. |
| Membership expiry check at booking time | **Java Service Logic** | Business logic must compare the member's `membership_expiry_date` against the session's `session_date` and reject with informative HTTP 400 messages. |
| Settlement window (`ATTENDED`/`NO_SHOW` only after session has begun) | **Java Service Logic** | Dependent on the current wall-clock timestamp relative to session date and time; best verified in application logic returning explicit HTTP 400 error payloads. |

## Deliberate Denormalisation

1. **`ClassSession.capacity` & `duration_minutes`:**
   - Instead of reading live values from `StudioClass` at query time, these are copied from `StudioClass` defaults upon session creation.
   - **Reason:** If a studio later updates the default capacity or duration of "Vinyasa Flow" from 20 to 25 spots or 60 to 75 minutes, already scheduled historical sessions and their booked limits must remain intact.
2. **Dynamic booking counts (avoiding denormalised counter columns):**
   - The system queries `COUNT(*)` of `BOOKED` and `WAITLISTED` statuses filtered by indexed `class_session_id` rather than keeping a mutable `current_booked_count` column on `ClassSession`.
   - **Reason:** Mutable counters are notorious for drift and race conditions during concurrent booking and cancellation. Counting over an indexed foreign key within a locked transaction is deterministic and fast.

## What Would Break First at 100x Data?

1. **`COUNT(*)` aggregation on large booking tables:**
   - With 100x data (e.g. millions of bookings), calculating live counts for dashboard summaries and session lists on the fly without caching or pre-aggregated rollups would introduce query latency. Partitioning `bookings` by `session_date` (or `class_session_id`) or maintaining indexed materialized views for past sessions would be the immediate remedy.
2. **`session_co_instructors` join filtering:**
   - Searching sessions visible to instructors via `LEFT JOIN session_co_instructors` could slow down without composite indexes on `(instructor_id, session_id)`.
3. **Pessimistic locking contention on viral drop sessions:**
   - If hundreds of users attempt to book the exact same high-demand session simultaneously, row-level locks on `ClassSession` would queue incoming DB connections, potentially hitting connection pool limits. A Redis-backed token bucket or reservation queue would be required before hitting the database.
